Submission limit: unlimited submissions within 2 weeks after the start date

In this phase, you will build an agent that automatically generates or organizes a mini training framework. The generated framework should load a suitable model architecture from HuggingFace, prepare a dataset of your choice, run a complete training loop, log training behavior, save and resume checkpoints, and measure training speed. The final assessment will be based on your report, your system design, your experiments, and your reflection.

Training speed is an important optimization goal, but there will be no speed leaderboard. Your report should demonstrate that the generated framework works, that your agent made meaningful design or optimization decisions, and that you understand the training-system issues you encountered.

This phase is designed for honor-track students. You are not expected to reproduce PyTorch, HuggingFace Trainer, DeepSpeed, Megatron, or PyTorch Lightning. Instead, your agent should generate or organize the key pieces that make a training framework work together:

```text
config -> data -> model -> optimizer -> scheduler -> training loop -> logging -> checkpoint -> resume
```

Your agent may use PyTorch and HuggingFace model/tokenizer/config utilities, but the training loop and framework organization should be generated or assembled by your own system.

---

## 1. Project Goal

Build an agent that can create a mini training framework to train a small language model on a dataset of your choice.

The training framework generated by your agent should support:

- loading a suitable model architecture or model configuration from HuggingFace
- constructing a model from the configuration
- loading and tokenizing a suitable dataset
- building train and validation dataloaders
- running a standard training loop
- using an optimizer and learning-rate scheduler
- logging metrics to TensorBoard
- saving checkpoints
- resuming training from a checkpoint
- reporting training behavior through logs, plots, and analysis
- measuring and improving training speed

The dataset does not need to be large. A small dataset that allows fast iteration and clear feedback is preferred. The model should also be chosen to match your available hardware; for example, a HuggingFace architecture around the scale of Qwen3-0.6B is a reasonable target if your GPU can train it. Smaller models are also acceptable if they help your agent iterate and expose useful training feedback.

The emphasis is not on training the strongest model. The emphasis is on building an agentic workflow that can construct, run, inspect, and improve a training framework, while helping you understand how framework components interact and how design choices affect training speed.

## 2. Suggested Code Structure

Your agent may generate or maintain code however you like, but the following structure is recommended for the generated training framework:

```text
training_framework/
  data.py
  model.py
  optim.py
  scheduler.py
  trainer.py
  checkpoint.py
  logger.py
configs/
  example.yaml
train.py
```

The following sections explain the expected role of each generated module.

### `data.py`

Responsible for data processing and dataloader construction.

Suggested responsibilities:

- choose and read a suitable text dataset
- call the tokenizer
- build train / validation splits
- convert text into token sequences
- support truncation or sequence packing
- build a `torch.utils.data.Dataset`
- build a `DataLoader`
- return batches such as `input_ids`, `labels`, and optionally `attention_mask`

This is one of the most important modules because data loading and tokenization often become real training bottlenecks. Your agent should choose or be configured with a dataset that is small enough for repeated experiments, but realistic enough to exercise the training pipeline.

### `model.py`

Responsible for model and tokenizer construction.

Suggested responsibilities:

- load or download a suitable HuggingFace model architecture or config, such as a small Qwen, GPT-style, or LLaMA-style model
- create the model from the config
- load the tokenizer
- optionally load pretrained weights
- optionally configure dtype, gradient checkpointing, or other model-level options
- report model size or parameter count

Your agent may use utilities such as `AutoConfig`, `AutoTokenizer`, and `AutoModelForCausalLM`. It should not use HuggingFace `Trainer` as the training framework. Choose a model scale that lets the agent see feedback quickly during training. A model around Qwen3-0.6B can be a useful reference point, but it is not a strict requirement.

### `optim.py`

Responsible for optimizer construction.

You do not need to implement AdamW from scratch. This file can wrap existing PyTorch optimizers and connect them to your config system.

Suggested responsibilities:

- build an optimizer from config
- support AdamW at minimum
- optionally support SGD, Adam, Adafactor, Lion, or other optimizers
- optionally implement your own optimizer if you are interested
- support parameter groups, such as weight-decay and no-weight-decay groups
- expose optimizer hyperparameters clearly through config

The purpose of `optim.py` is to make the framework flexible. Your agent is encouraged to support more optimizers, whether implemented by itself or provided by PyTorch or another allowed library.

### `scheduler.py`

Responsible for learning-rate scheduler construction.

You do not need to implement scheduler algorithms from scratch. This file can wrap PyTorch or HuggingFace scheduler utilities and connect them to your config system.

Suggested responsibilities:

- build a scheduler from config
- support at least one warmup-based schedule
- optionally support constant, linear decay, cosine decay, cosine with restarts, step decay, or polynomial decay
- optionally implement your own scheduler if you are interested
- make scheduler behavior visible through TensorBoard logging

The purpose of `scheduler.py` is to make training policy configurable and extensible. Your agent can use this module to explore different training policies.

### `trainer.py`

Responsible for the main training and validation loops.

Suggested responsibilities:

- initialize or receive model, dataloader, optimizer, scheduler, logger, and checkpoint manager
- run the training loop
- compute loss
- call `backward()`
- support optimizer step and scheduler step
- call `zero_grad()`
- optionally support gradient clipping
- optionally support gradient accumulation
- run validation periodically
- trigger logging
- trigger checkpoint saving
- support resuming from a checkpoint
- measure step time and throughput

This is the core of the framework. It should make the training process explicit and understandable.

### `checkpoint.py`

Responsible for saving and restoring training state.

Suggested responsibilities:

- save model state
- save optimizer state
- save scheduler state
- save global step
- save config
- optionally save random number generator states
- restore the above states during resume
- verify that learning rate and global step continue correctly after resume

A checkpoint is more than model weights. A useful training checkpoint should preserve enough state to continue training.

### `logger.py`

Responsible for logging and observability.

Suggested responsibilities:

- create a TensorBoard `SummaryWriter`
- log training loss
- log validation loss or perplexity
- log learning rate
- log step time
- log tokens/sec or samples/sec
- optionally log GPU memory
- optionally write a plain text log

The purpose of logging is to make the training system observable. Your report should include evidence from these logs.

## 3. Required Functionality

The framework generated by your agent should support at least:

- model construction from a HuggingFace architecture or config
- tokenizer loading
- dataset loading
- train / validation split
- training loop
- validation loop
- optimizer construction
- scheduler construction
- TensorBoard logging
- checkpoint saving
- checkpoint resume
- a config file for experiment settings
- training speed measurement, such as step time or tokens/sec

Your agent may choose or be configured with the dataset, model size, and training length based on available hardware. A small dataset, a small model, and a short run are acceptable as long as the framework is complete, the behavior is clearly demonstrated, and you can discuss the training-speed bottlenecks observed by the agent and by you.

## 4. Operator and Kernel Reuse

To balance the workload, you may reuse operators or kernels that you wrote in previous phases. For example, if you implemented custom CUDA, Triton, or PyTorch operators for earlier project stages, your agent may integrate them into the training framework instead of rewriting everything from scratch.

You are also encouraged to continue improving those operators if they are useful for training speed. The goal of this phase is not to force you to rebuild all low-level kernels, but to make your agent organize a complete training framework and reason about where performance bottlenecks come from.

---

## 5. Optional Extensions

Your agent is encouraged to add features that make the framework more complete, such as:

- mixed precision training
- gradient accumulation
- gradient clipping
- activation checkpointing
- `torch.compile`
- multiple optimizers
- multiple scheduler policies
- tokenizer caching
- pre-tokenization or cached dataset preprocessing
- dataloader performance optimizations
- checkpoint cleanup, such as keeping only the latest N checkpoints
- profiling data loading time, forward time, backward time, and optimizer time
- throughput reporting in tokens/sec
- simple distributed data parallel training
- fine-tuning from pretrained weights

These are optional. A small, correct, well-explained agent-generated framework is better than a large system that is difficult to understand or reproduce.

- what you learned from debugging

The report does not need to be a formal paper. It should be a clear technical reflection that shows what your agent did, what framework it produced, what you understood, and what you learned.

## 8. Assessment Emphasis

The report will be assessed mainly on:

- completeness of the training framework
- clarity of the agent workflow
- clarity of system design
- evidence that the framework actually ran
- quality of experiments and logs
- quality of training-speed measurements and optimization analysis
- quality of debugging discussion
- depth of reflection and personal understanding
- ability to explain how training framework components interact
- ability to explain what your agent automated and what it did not automate

Training speed matters as a project goal, and you should try to improve it from a basic implementation. However, the final grade will not be based on a speed ranking. The most important question is not "Did you build the fastest or largest framework?" but:

```text
Can you clearly explain what your agent does,
what a training framework needs to do,
how the generated implementation works,
how you measured and improved training speed,
what problems you encountered,
and what you learned from building it?
```
